# Парсер протокола LX200

Как разбирать команды Meade LX200, которые присылают Stellarium, SkySafari и
пульт: как выглядит поток байтов, какие бывают ответы, как устроить код и в
каком порядке добавлять команды. Это проект, в коде ещё не реализован.

Соседние документы: [control-interfaces.md](control-interfaces.md) — каналы связи
(USB, Wi-Fi, пульт) и зачем нужен LX200; [fsm.md](fsm.md) — состояния монтировки,
в которые превращаются команды.

## 1. Что приходит по проводу

LX200 — это **поток символов**, а не готовые пакеты. Команды могут прийти:

```
по одной:        :GR#
склеенными:      :GR#:GD#            ← в одном пакете USB или TCP две команды
разорванными:    :Sr05:3  ...  5:17#  ← половина сейчас, половина через 10 мс
с мусором:       ##:GR#              ← некоторые программы шлют «#», чтобы сбросить буфер
```

Поэтому парсер читает **по одному байту** и собирает команду, пока не встретит `#`:

```
байт ':'        → начать новую команду (буфер очистить)
байт '#'        → команда готова → выполнить → отправить ответ
другой байт     → дописать в буфер (буфер переполнен → выбросить команду)
байт 0x06 (ACK) → особый случай: один байт без ':' и '#', ответ 'P' (полярная монтировка)
```

**Пустая команда** (`#` без `:` перед ним) просто игнорируется.

## 2. Строение команды

После `:` идёт буква-семейство, потом подкоманда, потом параметры:

```
:  G R  #             G = Get (прочитать)      R = RA
:  S r  05:35:17  #   S = Set (задать)         r = RA цели      параметр = 05:35:17
:  M e  #             M = Move (поехать)       e = east
:  Q e  #             Q = Quit (стоп)          e = east
:  Q  #               Q без буквы = стоп всего
:  R G  #             R = Rate (скорость)      G = Guide
:  C M  #             C = sync,  M = «синхронизировать по цели»
```

---

## 3. Виды ответов

Здесь легко ошибиться. Разные команды отвечают по-разному, и программа на
компьютере ждёт **точно** тот формат, который ей положен:

| Вид | Команды | Пример ответа |
|---|---|---|
| **Без ответа** | `:Me#` `:Qe#` `:Q#` `:RG#` `:U#` | ничего |
| **Один символ, без `#`** | `:Sr…#` `:Sd…#` | `1` (принято) или `0` (ошибка) |
| **Строка с `#`** | `:GR#` `:GD#` `:CM#` | `05:34:31#` |
| **Особый** | `:MS#` | `0` (поехал) **или** `1Ниже горизонта#` (ошибка с текстом) |

Если ответить лишним `#` или пропустить его, Stellarium зависнет в ожидании
или будет читать мусор.

## 4. Форматы координат

LX200 бывает в **коротком** и **длинном** формате. Переключает команда `:U#`:

| | Короткий | Длинный |
|---|---|---|
| RA (`:GR#`) | `HH:MM.T#` → `05:34.5#` (T — десятые доли минуты) | `HH:MM:SS#` → `05:34:31#` |
| DEC (`:GD#`) | `sDD*MM#` → `+22*00#` | `sDD*MM:SS#` → `+22*00:52#` |

На приёме (`:Sr`, `:Sd`) парсер должен понимать **оба** формата. Вместо `*`
(градус) некоторые программы шлют байт `0xDF`: это символ градуса в кодировке
старых пультов Meade. Принимать надо и `*`, и `0xDF`, и `:`.

**Внутри** прошивки строки не хранятся, только целые числа:

```
RA  = секунды времени        0 … 86 399        (05:35:17 → 5×3600 + 35×60 + 17 = 20 117)
DEC = угловые секунды   −324 000 … +324 000    (+22*00:52 → 22×3600 + 0×60 + 52 = 79 252)
```

Целые числа не накапливают ошибок округления, и их проще проверять.

## 5. Устройство кода: три слоя

```
 ┌─ транспорт ─────────────────────┐   USB / Wi-Fi TCP / ESP-NOW / BLE
 │  принимает байты, шлёт ответ     │   (у каждого канала СВОЙ буфер команды)
 └──────────────┬──────────────────┘
                │ байт
 ┌─ парсер LX200 (lx200.cpp) ──────┐   собирает ":...#", находит команду в таблице,
 │  строки ↔ числа                  │   разбирает параметры, формирует ответ
 └──────────────┬──────────────────┘
                │ вызовы с числами
 ┌─ API монтировки (mount.cpp) ────┐   mount_move(ось, направление), mount_set_target(ra, dec),
 │  ничего не знает про строки      │   mount_goto(), mount_get_radec(&ra, &dec) ...
 └──────────────┬──────────────────┘   внутри: motion_send() и математика неба
                ▼
           motion_task (FSM из fsm.md)
```

Почему так:
- **Свой буфер у каждого канала.** Если Stellarium по USB и телефон по Wi-Fi шлют
  одновременно, их байты не смешаются.
- **Парсер не двигает моторы сам.** Он вызывает API монтировки, а оно кладёт
  команды в очередь `motion_task`. Правило «двигает только одна задача» сохраняется.
- **Парсер — чистые функции.** На вход строка, на выход ответ. Такой код легко
  проверить: подать `":Sr05:35:17#"` и сравнить ответ с `"1"`.

**Таблица команд** вместо длинного `if/else`:

```cpp
// одна строка = одна команда: префикс → обработчик
static const lx200_cmd_t COMMANDS[] = {
    { "GR", cmd_get_ra    },
    { "GD", cmd_get_dec   },
    { "Sr", cmd_set_ra    },
    { "Sd", cmd_set_dec   },
    { "MS", cmd_goto      },
    { "Me", cmd_move_east },
    { "Q",  cmd_stop_all  },   // ← короткие префиксы ПОСЛЕ длинных ("Qe" раньше "Q")
    // ...
};
```

Новая команда = новая строка в таблице.

## 6. Защита

- **Переполнение:** буфер, например, 32 байта. Если `#` так и не пришёл, команда
  выбрасывается и парсер ждёт следующий `:`.
- **Зависший обрывок:** если после `:` не было `#` дольше ~1 с, буфер сбрасывается.
- **Неизвестная команда:** не отвечать ничего. Так делают реальные монтировки.
  Ответ «на всякий случай» сломал бы синхронизацию с программой.
- **Неверный параметр** (`:Sr25:99:99#`): ответить `0`.

## 7. Порядок добавления команд

| Этап | Команды | Что можно проверить |
|---|---|---|
| **1. Движение** | ACK, `:Mn#` `:Ms#` `:Me#` `:Mw#`, `:Qn#`…`:Qw#`, `:Q#`, `:RG#` `:RC#` `:RM#` `:RS#` | двигать монтировку из терминала. **Математика не нужна** |
| **2. Где телескоп** | `:GR#` `:GD#` `:U#` `:CM#` | Stellarium показывает на карте, куда смотрит телескоп |
| **3. GoTo** | `:Sr…#` `:Sd…#` `:MS#` | наведение из Stellarium |
| **4. Время и место** | `:SC` `:SL` `:SG` `:St` `:Sg` и их `G`-пары | время с компьютера, без RTC |
| **5. Информация** | `:GVP#` (имя устройства), `:GVN#` (версия) | некоторые программы спрашивают это при подключении |

Этап 1 ложится прямо на то, что уже есть: `:Me#` → `CMD_SLEW_RUN`,
`:Qe#` → `CMD_STOP`. После появления FSM — на `CMD_MOVE` / `CMD_STOP` /
`CMD_SET_RATE` из [fsm.md](fsm.md).

## 8. Как проверять без Stellarium

Подключить разъём **USB** платы к компьютеру (разъём COM остаётся под прошивку
и логи) и открыть терминал, например `screen /dev/cu.usbmodemXXXX 9600`
(скорость любая) или CoolTerm с включённым Local Echo. Потом вводить команды руками
в английской раскладке. `screen` не показывает набранное — это нормально:
результат видно по монтировке и по логам на разъёме COM.

```
:RS#       (скорость перекладки)
:Me#       → ось RA поехала
:Qe#       → остановилась
:GR#       → 05:34:31#
```

Когда в терминале всё отвечает правильно, подключать Stellarium.

## 9. Что решить перед реализацией

1. ✅ **Канал для начала:** разъём USB платы (встроенный USB-Serial-JTAG),
   `main/lx200/lx200_usb.cpp`. Разъём COM (UART0) — прошивка и логи
   (см. [control-interfaces.md](control-interfaces.md), раздел 3.5).
2. **Порядок:** начать с этапа 1 (только движение) на текущих командах
   `CMD_SLEW_RUN`/`CMD_STOP`, или сначала сделать FSM из [fsm.md](fsm.md) и
   подключать парсер уже к ней.
3. **Ответы на неизвестные и неверные команды:** проверить на практике, как
   реагирует Stellarium (по логу обмена).
4. **Ответ на ACK:** `P` (полярная) или `G` (немецкая экваториальная) — проверить,
   какой ждут Stellarium и SkySafari.
