# Обработка ошибок драйвера TMC2209

Как программа обнаруживает ошибки драйвера, кто и как на них реагирует,
когда мотор выключается и когда включается обратно.

Код: [tmc-uart.cpp](../main/tmc-driver/tmc-uart.cpp) (обмен по UART),
[tmc-driver.cpp](../main/tmc-driver/tmc-driver.cpp) (настройка),
[tmc-error.cpp](../main/tmc-driver/tmc-error.cpp) (сторож),
[tmc-err-codes.h](../main/utils/tmc-err-codes.h) (свои коды ошибок).

Соседние документы: [tmc-algorithm.md](tmc-algorithm.md) — настройка драйвера,
[todo.md](todo.md) — что ещё не сделано.

## 1. Общая схема: кто сообщает, кто решает

Главное правило: **нижние уровни только сообщают об ошибке (возвращают код),
решает и выключает моторы одно место.**

```
 Уровень 1: UART (tmc-uart.cpp)
   read_tmc_reg / write_tmc_reg → NO_RESPONSE, INVALID_CRC, WRITE_LOST, ошибка отправки
   Только возвращает код. Ничего не выключает.
        │
        ▼
 Уровень 2: операции (tmc-driver.cpp)
   tmc_init_step_0..11, tmc_check_connection, tmc_check_overheat ...
   Передают код наверх (иногда заменяют на более понятный). Ничего не выключают.
        │
        ▼
 Уровень 3: кто РЕШАЕТ
   ├─ старт:  handle_drivers_connection + app_main   → «не включать» ось     (раздел 3)
   └─ работа: сторож tmc_watchdog_task               → «выключить» / «включить» (разделы 4–8)
                 axis_shutdown() — ЕДИНСТВЕННОЕ место выключения
                 axis_restore()  — ЕДИНСТВЕННОЕ место включения
```

На старте мотор ещё ни разу не включался (шаг 0 настройки ставит `ENN = 1`),
поэтому при ошибке ось просто **не включается**. В работе мотор уже под током,
и его нужно **выключить** — это делает только сторож.

## 2. Коды ошибок

`esp_err_t` — это просто `int`. Свои коды начинаются с `0x20000`, выше всех кодов
ESP-IDF. Для логов — `tmc_err_to_name(err)`: `esp_err_to_name()` свои коды не знает
и пишет `UNKNOWN ERROR`.

| Код | Значение | Кто возвращает |
|---|---|---|
| `ESP_ERR_TMC_NO_RESPONSE` | ответ не пришёл или пришёл не весь | `read_tmc_reg`, `set_IFCNT_reg` (→ `write_tmc_reg`) |
| `ESP_ERR_TMC_INVALID_CRC` | ответ пришёл, но испорчен (sync, адрес или CRC) — обычно помеха | `read_tmc_reg`, `set_IFCNT_reg` |
| `ESP_ERR_TMC_WRITE_LOST` | запись отправлена, но счётчик `IFCNT` не вырос на 1 | `write_tmc_reg` |
| `ESP_ERR_TMC_WRONG_CHIP` | версия в `IOIN` не `0x21` — это не TMC2209 | шаг 1, `tmc_check_connection` |
| `ESP_ERR_TMC_ENN_LOW` | `ENN = 0` до настройки (нет подтяжки EN) | шаг 1 |
| `ESP_ERR_TMC_VERIFY_FAILED` | записанное в `CHOPCONF` не совпало с прочитанным | шаг 11 |
| `ESP_ERR_TMC_RA_NOT_CONFIGURED` | драйвер RA не настроен — работать нельзя | `handle_drivers_connection` |
| `ESP_ERR_TMC_DEC_NOT_CONFIGURED` | драйвер DEC не настроен — RA работает | `handle_drivers_connection` |

Стандартные коды ESP-IDF, которые тоже встречаются:

| Код | Где | Значение |
|---|---|---|
| `ESP_ERR_TIMEOUT` | шаг 1 | драйвер не ответил за ~2 с (нет VS) — на старте RA повторяется |
| `ESP_ERR_NOT_ALLOWED` | шаг 2 | в `GSTAT` горит `drv_err` или `uv_cp` |
| `ESP_ERR_INVALID_STATE` | `tmc_check_connection` | пины MS1/MS2 дают не тот адрес |
| `ESP_ERR_INVALID_STATE` | `stepper_*` | движение заблокировано после аварии |

**Переход IFCNT через 255.** `IFCNT` — 8-битный счётчик, после 255 идёт 0.
Поэтому разность считается «по кругу»: `(uint8_t)(after - before) != 1`.
Без приведения `0 - 255 = -255` давало бы ложный `WRITE_LOST` на каждой 256-й записи.

## 3. Ошибки при старте

`handle_drivers_connection()` в [tmc-driver.cpp](../main/tmc-driver/tmc-driver.cpp):

```
tmc_check_connection(RA)           — только лог
tmc_check_connection(DEC) == OK ?  → dec_connected

RA:  initialize_tmc_driver(RA)
       ESP_ERR_TIMEOUT  → повторять (ESP может загрузиться раньше, чем появится VS)
       другая ошибка    → return ESP_ERR_TMC_RA_NOT_CONFIGURED
DEC: только если dec_connected
       ошибка → return ESP_ERR_TMC_DEC_NOT_CONFIGURED
```

Шаг 1 повторяет чтение `IOIN` до ~2 с, пока приходит `NO_RESPONSE` или
`INVALID_CRC` (помеха). Остальные ошибки — сразу наверх.

`app_main`:

| Результат | Что делает |
|---|---|
| `ESP_OK` | включает обе оси, сторож следит за обеими |
| `ESP_ERR_TMC_DEC_NOT_CONFIGURED` | включает только RA, DEC остаётся `ENN = 1`, сторож следит только за RA |
| `ESP_ERR_TMC_RA_NOT_CONFIGURED` | `return` — без RA работать нельзя, моторы не включаются |

**Порядок запуска важен:**

```
handle_drivers_connection → stepper_init → tmc_driver_on(RA, DEC)
→ monitor_log_task → tmc_watchdog_watch(...) → tmc_watchdog_task
```

Сторож запускается **последним**. Иначе включать драйверы могли бы две задачи
сразу (`app_main` и сторож), а `stepper_emergency_stop()` в стороже читал бы
моторы, пока `stepper_init()` их ещё создаёт.

## 4. Как работает сторож

Отдельная задача FreeRTOS, которая каждые **100 мс** (`TMC_WATCHDOG_TASK_DELAY_MS`)
читает регистр `GSTAT` каждой проверяемой оси и, если нужно, `DRV_STATUS`.

Сторож помнит, в какой аварии находится ось (`fault[a]`). Это нужно, чтобы:
- обрабатывать каждую аварию **один раз**, а не 10 раз в секунду;
- понимать, когда причина ушла и ось можно включить обратно.

Откуда сторож берёт информацию:

| Регистр | Бит | Имя | Что значит |
|---|---|---|---|
| `GSTAT` | 0 | `reset` | драйвер перезагрузился, все настройки заводские |
| `GSTAT` | 1 | `drv_err` | драйвер сам отключился: перегрев **или** замыкание (защёлкивается) |
| `GSTAT` | 2 | `uv_cp` | низкое напряжение питания мотора (**не** защёлкивается, гаснет сам) |
| `DRV_STATUS` | 0 | `otpw` | драйвер нагрелся до 120 °C (предупреждение) |
| `DRV_STATUS` | 1 | `ot` | перегрев 143 °C — причина `drv_err` |
| `DRV_STATUS` | 2–5 | `s2g*`, `s2vs*` | короткое замыкание — причина `drv_err` |

### 4.1. Один цикл для одной оси — `watchdog_check_axis(a)`

```
прочитать GSTAT
│
├─ INVALID_CRC (помеха)?
│     счётчик < 5 → пропустить цикл (лог-предупреждение)
│     5 раз подряд (0.5 с) → считать как «нет ответа» ↓
│
├─ ошибка чтения?
│     ось работала (FAULT_NONE) → axis_shutdown(a, FAULT_NO_RESPONSE)
│     return
│
├─ ответ нормальный → счётчик помех = 0
│
└─ switch (fault[a]) — каждое состояние проверяет только своё:
      FAULT_NONE         → check_running:            нет ли новой аварии? + tmc_check_overheat
      FAULT_NO_RESPONSE  → check_no_response:        связь вернулась
      FAULT_OVERHEAT     → check_overheat_fault:     остыл ли?
      FAULT_UNDERVOLTAGE → check_undervoltage_fault: вернулось ли напряжение?
      FAULT_RESET        → axis_restore(a, true):    повторить перенастройку
      FAULT_SHORT        → ничего: ждём человека
```

**Почему одиночная ошибка CRC — не авария.** Ответ пришёл, значит драйвер жив —
просто помеха испортила бит по дороге. Если считать это аварией, один
искажённый байт останавливал бы обе оси и сбивал наведение. Отсутствие ответа
(`NO_RESPONSE`) — авария сразу: почти всегда это пропажа питания VS.

## 5. Какие аварии обрабатываются

### 5.1. Драйвер не отвечает — `FAULT_NO_RESPONSE`

| | |
|---|---|
| **Как обнаружить** | чтение `GSTAT` вернуло `NO_RESPONSE` (или `INVALID_CRC` 5 раз подряд) |
| **Частая причина** | пропало питание мотора VS (без него логика драйвера не работает), обрыв провода UART |
| **Что делает сторож** | `axis_shutdown(a, FAULT_NO_RESPONSE)`, дальше молча ждёт ответа |
| **Как выходит** | драйвер ответил: если в `GSTAT` горит `drv_err`/`uv_cp` — сразу переход в эту аварию; иначе `axis_restore(a, reset)` — с перенастройкой, если `reset = 1` |

Зачем `ENN = 1` сразу: если питание вернётся, драйвер **сам** не включится
с заводскими настройками (ток от подстроечника, микрошаг 1/8) и вал не дёрнется.

### 5.2. Низкое напряжение — `FAULT_UNDERVOLTAGE`

| | |
|---|---|
| **Как обнаружить** | `GSTAT.uv_cp = 1` |
| **Частая причина** | просадка блока питания или аккумулятора, плохой контакт |
| **Что делает сторож** | `axis_shutdown(a, FAULT_UNDERVOLTAGE)` |
| **Как выходит** | `uv_cp` погас сам → `axis_restore(a, reset)` |

Если горят и `uv_cp`, и `drv_err`, приоритет у `uv_cp`: при низком напряжении
`drv_err` часто его следствие.

### 5.3. Перегрев — `FAULT_OVERHEAT`

| | |
|---|---|
| **Как обнаружить** | `GSTAT.drv_err = 1` и `DRV_STATUS.ot = 1` |
| **Частая причина** | большой ток `IRUN`, нет радиатора, жарко |
| **Что делает сторож** | `axis_shutdown(a, FAULT_OVERHEAT)` + подробный лог `DRV_STATUS`. Дальше раз в 100 мс проверяет температуру |
| **Как выходит** | `ot = 0` **и** `otpw = 0` (остыл ниже 120 °C) → сбросить `drv_err` записью 1 → `axis_restore(a, reset)` |

Если сброс `drv_err` не прошёл по UART — ось не включается, повтор в следующем
цикле. Иначе `drv_err` остался бы гореть, и шаг 2 перенастройки возвращал бы ошибку.

### 5.4. Короткое замыкание — `FAULT_SHORT`

| | |
|---|---|
| **Как обнаружить** | `GSTAT.drv_err = 1` и `DRV_STATUS.ot = 0` (значит причина — `s2ga/s2gb/s2vsa/s2vsb`) |
| **Частая причина** | повреждённый провод мотора, провод касается корпуса |
| **Что делает сторож** | `axis_shutdown(a, FAULT_SHORT)` + подробный лог `DRV_STATUS` |
| **Как выходит** | **автоматически — никогда.** Включение при замыкании может повредить драйвер. Только вручную: проверить провода, перезагрузить ESP |

Если при `drv_err` не удалось прочитать `DRV_STATUS`, причину узнать нельзя —
сторож считает худшее, то есть замыкание.

### 5.5. Перезагрузка драйвера — `FAULT_RESET`

| | |
|---|---|
| **Как обнаружить** | `GSTAT.reset = 1` при `fault = FAULT_NONE`, или при выходе из другой аварии |
| **Частая причина** | питание драйвера пропадало (короткий провал VS) |
| **Опасность** | драйвер работает на заводских настройках: ток от подстроечника VREF, микрошаг 1/8 вместо 1/256 — мотор крутится в 32 раза быстрее |
| **Что делает сторож** | `axis_shutdown(a, FAULT_RESET)` → `axis_restore(a, true)`: полная настройка `initialize_tmc_driver()`, сброс защиты от перегрева, `ENN = 0` |
| **Если настройка не удалась** | ось остаётся в `FAULT_RESET`, повтор через 100 мс |

**Зачем отдельное состояние.** Шаг 2 настройки стирает флаг `reset` в `GSTAT`.
Если настройка упадёт на шаге 3..11, по `GSTAT` уже не видно, что её нужно
повторить: без `FAULT_RESET` сторож решил бы, что всё в порядке, а мотор остался
бы выключенным навсегда.

### 5.6. Предупреждение о нагреве — `otpw` (не авария)

Обрабатывается функцией `tmc_check_overheat(a)`, только в `FAULT_NONE`.
`GSTAT` сообщает только о том, что **уже случилось** (143 °C, мотор выключен).
Предупреждение при 120 °C есть только в `DRV_STATUS`, поэтому его читают отдельно.

```
  до 120 °C   норма
  120 °C      otpw = 1   ← предупреждение: снизить ток, мотор работает дальше
  143 °C      ot = 1     ← авария: драйвер сам отключил мотор (5.3)
```

| | |
|---|---|
| **Как обнаружить** | `DRV_STATUS.otpw = 1` |
| **Что делает** | снижает ток в движении: `irun` → `irun_hot` (RA 702 → 580 мА: тепла ≈ в 1.5 раза меньше, т.к. нагрев ∝ I²) |
| **Как выходит** | `otpw` нет **30 секунд подряд** → возвращает `irun`. Пауза нужна, чтобы ток не прыгал туда-обратно около порога 120 °C |

Цель — не допустить настоящего перегрева (5.3) и обрыва ведения посреди ночи.
Если проверка не удалась по UART — предупреждение в лог, повтор в следующем цикле.

## 6. Схема состояний

```
                        ┌──────────────────────────────────────────────┐
                        │                  FAULT_NONE                  │
                        │             (нормальная работа)              │
                        │          tmc_check_overheat() — otpw         │
                        └──┬──────────┬──────────┬──────────┬──────┬───┘
               нет ответа  │  uv_cp   │ drv_err  │ drv_err  │reset │
               (или CRC×5) │          │ + ot     │ без ot   │      │
                           ▼          ▼          ▼          ▼      ▼
                  ┌──────────────┐┌────────────┐┌──────────┐┌───────┐┌─────────┐
                  │ NO_RESPONSE  ││UNDERVOLTAGE││ OVERHEAT ││ SHORT ││  RESET  │
                  │ ждать ответа ││ ждать      ││ ждать    ││ выхода││ настро- │
                  │              ││ uv_cp = 0  ││ < 120 °C ││  нет  ││ ить     │
                  └──────┬───────┘└─────┬──────┘└────┬─────┘└───────┘└──┬──┬───┘
                 ответил │      uv_cp=0 │   остыл,   │   (только        │  │ не
                         │              │   сброс    │    вручную)      │  │ удалось
                         │              │   drv_err  │                  │  └──► повтор
                         ▼              ▼            ▼                  ▼        через 100 мс
                  ┌───────────────────────────────────────────────────────┐
                  │                axis_restore(a, reset)                 │
                  │  reset = 1 → initialize_tmc_driver (не удалось → RESET)│
                  │  ENN = 0 + 200 мс (AT#1) → FAULT_NONE                 │
                  │  все оси в норме? → stepper_unblock()                  │
                  └───────────────────────────────────────────────────────┘
```

Из `NO_RESPONSE` можно перейти и сразу в другую аварию: если драйвер ответил,
а в `GSTAT` горит `drv_err` или `uv_cp`.

**Уйти** из `FAULT_NONE` можно только через `axis_shutdown()`,
**вернуться** — только через `axis_restore()`.

## 7. Выключение и включение: axis_shutdown / axis_restore

### 7.1. `axis_shutdown(a, reason)` — единственное место выключения

```
1. stepper_emergency_stop()   флаг «движение запрещено» + forceStop ВСЕХ осей,
                              ждёт, пока импульсы STEP прекратятся
2. tmc_driver_off(a)          ENN = 1 — обесточить мотор оси a
3. fault[a] = reason          по причине сторож решает, когда и как включать обратно
```

**Почему сначала стоп, потом ENN.** В обратном порядке несколько миллисекунд
FastAccelStepper ещё слал бы шаги обесточенному мотору и считал бы их сделанными —
позиция в программе убежала бы от реальной. При перегреве, замыкании и низком
напряжении драйвер обесточивает мотор сам, там порядок не важен; при `reset`
и потере связи — важен.

**Остановка — аварийная** (`forceStop`), без плавного торможения: торможение
по рампе — это лишние импульсы, которые драйвер в заводском режиме исполнит
в 32 раза крупнее.

### 7.2. `axis_restore(a, was_reset)` — единственное место включения

```
was_reset?
  да → fault[a] = FAULT_RESET          запомнить ДО настройки
       initialize_tmc_driver(a)        шаг 0 внутри: ENN = 1
         не удалось → лог, return      остаёмся в FAULT_RESET, повтор через 100 мс
       tmc_overheat_reset(a)           шаг 5 записал полный ток irun
tmc_driver_on(a)                       ENN = 0 + 200 мс (AT#1)
fault[a] = FAULT_NONE
все проверяемые оси в норме? → stepper_unblock()   (раздел 8)
```

**Драйвер включается только настроенным.** Если драйвер перезагружался, его
регистры заводские — включить его без перенастройки значит дать мотору
заводской ток и микрошаг 1/8.

## 8. Блокировка движения

Флаг `motion_blocked` ([stepper.cpp](../main/stepper/stepper.cpp)):
- ставит `stepper_emergency_stop()` (из `axis_shutdown`);
- снимает `stepper_unblock()` — **вызывает только сторож** в `axis_restore`;
- проверяют `stepper_run_mhz` и `stepper_move_to_async`: при блокировке
  возвращают `ESP_ERR_INVALID_STATE` (плавный стоп `stepper_run_mhz(a, 0)`
  разрешён всегда); `motion_task` раз в 50 мс видит флаг и переходит в `FAULT`.

**Правило снятия (вариант А): автоматически, когда ВСЕ проверяемые оси
в `FAULT_NONE`** (`all_watched_axes_ok()`).

| Ситуация | Результат |
|---|---|
| перегрелась одна ось, потом остыла | остальные в норме → движение разрешено |
| пропало VS, RA вернулась первой | DEC ещё в аварии → блокировка остаётся |
| затем вернулась DEC | все в норме → движение разрешено |
| на одной оси замыкание | блокировка до перезапуска ESP |

**Почему нет гонки.** Выключение (`axis_shutdown`) и разблокировку
(`axis_restore`) делает одна задача — сторож. Ситуация «проверил, что всё
в норме → в этот момент другая задача выключила ось → разблокировал» невозможна.
Поэтому другие задачи **не должны** вызывать `stepper_unblock()` сами.

**После разблокировки моторы стоят.** `forceStop` остановил всё, в том числе
ведение. Разблокировка только снимает запрет:

```
ведение → авария → стоп → восстановление → «движение разрешено»
→ мотор СТОИТ, ведение выключено, звезда уплывает
```

Нужно проверить наведение (позиция могла сбиться) и снова запустить ведение
командой `CMD_TRACK_START`. Об этом пишет лог при разблокировке.

## 9. Ограничения

- **Провал питания короче 100 мс** сторож может не заметить: драйвер включится сам
  (`ENN = 0`) с заводскими настройками раньше, чем пройдёт проверка. Мгновенно
  обнаружить пропажу питания можно только «железом» (например, делитель VS на АЦП).
- **Рывок при включении неизбежен.** При `ENN = 0` после аварии вал перескакивает
  к началу синусоиды тока — до ±2 полных шагов (±3.6° на валу, ≈ ±0.03° по RA).
  Драйвер не помнит положение обмоток без питания.
- **Выход из `FAULT_SHORT`** — только перезагрузкой ESP.
- **Перенастройка блокирует сторож** до ~2.5 с (ожидание ответа в шаге 1 + AT#1):
  в это время другие оси не проверяются.
- **Ведение после аварии само не возобновляется** (раздел 8).
- **UART общий для всех задач.** `tmc_read` / `tmc_write` сами берут мьютекс
  `tmc_uart_mutex` на время одного обмена, поэтому их можно вызывать из любой
  задачи без дополнительной защиты. Самому брать этот мьютекс не нужно: если взять
  его и затем вызвать `tmc_read`, задача будет ждать сама себя вечно.

## 10. Две оси

### 10.1. Какие оси проверяются

Сторож проверяет только оси, включённые через `tmc_watchdog_watch(a)` (вызывается
в `app_main` до запуска задачи): RA — всегда, DEC — только если его драйвер
успешно настроен. Иначе не подключённый DEC сторож считал бы аварией и
останавливал бы **все** оси, в том числе работающую RA.

### 10.2. Политика

| Что случилось | Моторы | Драйверы |
|---|---|---|
| авария на **любой** оси | `stepper_emergency_stop()` останавливает **все** оси, движение блокируется (для наведения нужны обе оси) | выключается (`ENN = 1`) **только** драйвер сломавшейся оси |
| причина ушла / `reset` | движение разрешается, когда **все** проверяемые оси в норме (раздел 8) | перенастраивается и включается **только** этот драйвер |
| не отвечают **все** проверяемые драйверы | — | одно сообщение «вероятно, пропало общее питание моторов VS» |

### 10.3. Как устроено в коде

- Состояние аварии у каждой оси своё: `fault[AXIS_COUNT]`, счётчик помех —
  `crc_err_count[AXIS_COUNT]`.
- Проверка одной оси — `watchdog_check_axis(a)`; задача вызывает её для каждой
  проверяемой оси раз в 100 мс.
- Теги лога с именем оси: `tmc-watchdog RA`, `tmc-watchdog DEC`.
- Перенастройка (`initialize_tmc_driver`) ждёт ответа драйвера не дольше ~2 с,
  поэтому повторная пропажа питания во время перенастройки **не замораживает**
  сторож (см. [tmc-algorithm.md](tmc-algorithm.md), раздел 8.5).

### 10.4. Замечено на практике

- **Частые `reset` у DEC** (`tmc-watchdog DEC: Драйвер перезагрузился`) — признак
  просадки питания или плохого контакта у модуля DEC: драйвер сбрасывается при
  провале любого из питаний VS, 5VOUT или VCC_IO (datasheet стр. 71). Проверить:
  VS/GND проводами прямо к модулю, конденсатор 100 мкФ у VS, надёжный 3.3 В на
  VCC_IO и MS1, проводку мотора DEC. Диагностика: отключить мотор DEC; поменять
  модули RA и DEC местами — проблема «уйдёт за модулем» или останется на месте.
